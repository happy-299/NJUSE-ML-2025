# Level1-Task3 实验报告



## 1. 问题介绍

评审意见生成是代码评审自动化中的核心任务之一。其目标是根据提交的代码变更，自动生成自然语言形式的评审意见，以辅助代码审查者发现潜在问题、优化代码质量 。



- **输入**：代码变更数据，通常以 Diff Hunk 形式呈现，包含增加行、删除行及上下文。
- **输出**：针对该变更的评审意见序列 。



## 2. 数据预处理

1. **Diff 格式标准化**：
   - 将代码 Diff 中的 `+`（新增行）标记替换为特殊 Token `[ADD]`。
   - 将 `-`（删除行）标记替换为 `[DEL]`。
   - 未变更的上下文行标记为 `[KEEP]`。
2. **序列截断与填充**：
   - **Max Source Length**: 300。代码变更序列超过 300 Token 的部分被截断，不足部分使用 `[PAD]` 填充。
   - **Max Target Length**: 128。评审意见超过 128 Token 的部分被截断。
3. **数据采样策略**：
   - 受限于本地实验环境（无 GPU，仅 CPU），本实验采用了随机采样策略以缩短实验周期。
   - **训练集**：从原始训练集（约 11.8 万条）中随机抽取 **3,000 条** 样本。
   - **测试集**：原始测试集。



## 3. 方法与实现 

本实验复现了 CodeReviewer 论文中提出的基于预训练模型的评审意见生成方法。为了在本地受限的计算资源（CPU 环境）下完成实验，在模型微调和推理策略上进行了特定的适配与优化。



### 3.1 LLM 模型选择

本实验选用 **CodeT5-base** 作为基础模型。

- **模型架构**：CodeT5 是基于 Encoder-Decoder 结构的 Transformer 模型，在大量代码语料上进行了预训练，具备优秀的代码理解与生成能力，特别适合处理代码差异到自然语言的转换任务。
- **参数规模**：约 2.2 亿参数，相比于 CodeT5-large 或其他百亿参数模型，CodeT5-base 在保持良好性能的同时，更适合本地微调实验。



### 3.2 提示设计与数据预处理

为了使模型能够准确理解代码变更的语义，采用了特定的输入表示方法：

1. **Diff 格式标准化**：
   - 原始的 Git Diff 包含 `+`（新增）、`-`（删除）等符号。将这些符号替换为模型专用的特殊 Token，以显式区分代码状态：
     - **[ADD]**：标记新增的代码行。
     - **[DEL]**：标记被删除的代码行。
     - **[KEEP]**：标记未变更的上下文代码行。
   - 这种显式标记有助于 Encoder 更清晰地捕捉代码变更的结构信息。
2. **序列截断与填充**：
   - **源序列（输入）**：最大长度设为 **300 Token**。超过部分截断，不足部分使用 `[PAD]` 填充。这覆盖了大多数代码变更片段的长度。
   - **目标序列（输出）**：最大长度设为 **128 Token**。用于生成评审意见。



### 3.3 微调策略

针对本地 CPU 环境算力不足的限制，采用了以下轻量化微调策略：

1. **数据采样（Data Sampling）**：
   - 放弃全量数据（11.8万条），采用随机采样策略构建轻量级数据集。
   - **训练集**：随机抽取 **3,000 条** 样本。
   - **测试集**：全集。
   - 此策略在保留数据分布特征的同时，将训练时间压缩至可接受范围（3 - 4 小时）。
2. **超参数配置**：
   - **优化器**：使用 AdamW 优化器，配合线性 Warmup 策略，以稳定训练过程。
   - **学习率 (Learning Rate)**：设为 `3e-4`。
   - **批次大小 (Batch Size)**：设为 `2`。
   - **训练轮次 (Epochs)**：设定为 `1` 轮。对于采样后的数据集，模型在 1 个 Epoch 后即可收敛并学会基本的输出格式。
3. **推理优化**：
   - 在测试阶段，将 **Beam Size 设为 1**，替代论文中常用的 Beam Search（通常为 5）。
   - 虽然这在一定程度上降低了生成的多样性，但在 CPU 环境下将推理速度提升了约 5 倍，确保了实验的可行性。



## 4. 结果与分析

| **指标 (Metric)** | **本实验结果 (Ours)** | **论文基线 (CodeT5-base)** |
| ----------------- | --------------------- | -------------------------- |
| **BLEU-4**        | **0.00**              | 4.83                       |
| **ROUGE-L**       | **1.41**              | -                          |
| **BERTScore F1**  | **81.11**             | -                          |



### 4.1 结果分析

1. **BLEU-4 (0.00)**：
   - BLEU-4 分数极低符合预期。BLEU 衡量的是 4-gram 的精确匹配。由于本实验仅使用了 **2.5%** 的训练数据且仅训练了 **1 个 Epoch**，模型尚未能学会生成与参考答案完全一致的长短语。此外，代码评审意见通常具有极高的多样性，即使语义相近，用词不同也会导致 BLEU 为 0。
2. **BERTScore (81.11)**：
   - BERTScore 较高，说明模型生成的文本在 **语义层面** 与参考答案保持了一定的相似性。这表明代码跑通且模型已具备基本的自然语言生成能力，而非生成乱码。
3. **复现限制因素**：
   - **数据量差异**：论文使用了全量数据（118k）训练，而本实验仅用了 3k。
   - **搜索策略**：Greedy Search (Beam=1) 倾向于生成高频、通用的短句，不如 Beam Search 生成的质量高。



## 5. 结论

本实验成功在资源受限的本地 CPU 环境中复现了 CodeReviewer 的评审意见生成任务。虽然受限于算力和时间，模型性能（BLEU）未达到 SOTA 水平，但完整跑通了从数据预处理、模型微调、推理生成到多维度评估（BLEU/ROUGE/BERTScore）的全流程，验证了实验代码的正确性和 CodeT5 模型在代码评审场景下的适用性。
